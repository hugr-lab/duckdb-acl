# Spec 007: offline JWT verification (issuers, role mappings, EntraID)

- **Status**: implemented
- **Date**: 2026-08-20
- **Author**: hugr-lab

## Summary

Phase 2 of the role-aware resolver (design: `design/002-role-aware-resolver`, local): the `ACL
TOKEN` form gets real, fully offline JWT verification — RS256/ES256/HS256 signatures, standard
claims, an issuer registry with per-issuer audiences/algorithms/claim mapping, and external→role
mappings (EntraID app roles and groups included). Multi-role principals become real: a token's
roles resolve as the union of their grants. No network IO anywhere: keys are data in the issuer
config, rotated by the gateway or admin.

## Problem

`ACL TOKEN` verified against an in-memory stub map — fine for tests, useless in production, where
the gateway hands DuckDB real JWTs from one or more identity providers (EntraID among them) and the
extension must verify them offline (pool-safe, no per-request introspection) and derive roles and
claim values from them.

## Design

- **Crypto with zero new dependencies**: duckdb's bundled mbedtls provides RSA-PKCS1v15 + SHA-256 +
  HMAC (RS256, HS256); ES256 comes from the vendored **p256-m** (`third_party/p256-m`, Apache-2.0,
  ~1.5k lines, constant-time, by an mbedtls maintainer) — the trimmed mbedtls carries no ECDSA, and
  JOSE's raw `r||s` signatures / JWKS `x`,`y` keys are exactly p256-m's API, so no ASN.1 is
  involved. (One local patch: its 32-bit Arm asm gate excludes `__aarch64__`.) JSON via bundled
  yyjson. `duckdb_mbedtls` links into the loadable artifact too — the host binary does not export
  mbedtls symbols.
- **Issuer registry** — `acl_define_issuer(issuer, keys_json, audiences_csv, algs_csv, role_claim,
  claim_map_json)`: `keys_json` is a JWKS (`RSA` n/e, `EC` P-256 x/y, `oct` k) or a PEM public key;
  `algs` is an allowlist (anything else, including `none`, is refused); `role_claim` is a dot path
  (`roles`, `realm_access.roles`, `groups`); `claim_map` maps JWT paths to `acl_claim` names
  (`{"tid": "tenant"}`). Stored in memory (dev) or in the catalog (`acl.issuers`,
  `acl.role_mappings` — both with primary keys); an enabled catalog is the exclusive source, like
  every other resolver.
- **Verification flow** (`src/acl_token.cpp`, pure functions): a token that parses as a JWT always
  takes this path — it can never fall back to the dev stub. Signature per the issuer's allowlist →
  `exp`/`nbf` with `acl_jwt_clock_skew` (setting, default 60s) → `aud` (string or array) must
  intersect the issuer's allowlist → role and claim extraction. Failures throw with a specific
  reason (the gateway is trusted with diagnostics; denials must throw under FALLBACK anyway).
  Non-JWT tokens keep the in-memory `acl_define_token` stub (dev bridge).
- **Roles**: values of the role claim map through `acl_map_role(issuer, source, external_value,
  role)` — one value may map to several roles; an unmapped value is accepted as an internal role
  only if that role is actually known (registered/granted), otherwise ignored. Zero resulting roles
  ⇒ rejection. The principal carries the full role vector; grants resolve as the union (spec 006).
- **EntraID**: app roles arrive in `roles` (plain `role_claim`); security groups via
  `role_claim = 'groups'` + GUID mappings. **Groups overage** (the claim replaced by a Graph link)
  is refused loudly with instructions — the extension is offline by design; resolving via Graph is
  the gateway's job (ROLE form).
- **Claims**: `claim_map` extraction first, then the roles' default claims (explicit token claims
  win) — memory and catalog sides both merged, as before.

## Enforcement & security

The alg allowlist is per issuer and closed (no `none`, no cross-alg confusion: the key type is
selected by the verified alg). HS256 comparison is constant-time. `exp` is mandatory. Keys are
admin-supplied data (existing trust model); no network IO exists in the verification path, so a
pool of instances stays deterministic. A JWT-shaped token that fails anything throws — it can never
degrade into the dev-stub lookup. Unknown issuer, unmapped roles, and groups overage all fail
closed with distinct messages.

## Testing

`test/sql/acl_jwt.test` (52 assertions), tokens and keys generated by
`test/scripts/gen_jwt_fixtures.py` (test-only keys, committed; regenerate fixtures and test
together): RS256 via JWKS and via PEM, ES256 (JWKS x/y), HS256 (oct k) including the alg-allowlist
flip, claim mapping into RLS (`tid` → `tenant`), multi-role union across two grants, EntraID group
GUID → role mapping, groups-overage refusal, and negatives — unknown issuer, expired token, wrong
audience, tampered payload (valid JSON, broken signature), unknown role, plus the dev stub still
working and the issuer registry living in the catalog (`acl.issuers`). All other suites unchanged.

## Alternatives considered

- **OpenSSL / full mbedtls via vcpkg** — breaks the dependency-free core build (wasm/windows
  release artifacts build without vcpkg); p256-m is 1.5k lines and exactly the needed primitive.
- **JWKS auto-fetch from `.well-known`** — deliberately phase 2b (design): network IO off by
  default; the gateway rotates keys into the config.
- **Tokens as session state** — rejected long ago (spec 001): claims bake as constants, pool-safe.

## Follow-ups

- 2b: optional JWKS fetcher (`.well-known/openid-configuration` → `jwks_uri`, cache by `kid`).
- Verified-token cache keyed by `(policy_version, token)` if profiles show RSA verify per batch
  matters (~100µs today).
- ES384/ES512, RSA-PSS (PS256) if a provider demands them.
