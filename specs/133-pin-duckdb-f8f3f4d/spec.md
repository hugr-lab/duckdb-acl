# Spec 133: re-pin duckdb to f8f3f4d - quack e7a9be3, the scanners at their mains

- **Status**: implemented
- **Date**: 2026-10-17
- **Author**: the agent, at the owner's ask ("сейчас tresor переходит на свежую голову duckdb 2.0, давай мы тоже
  сделаем", "у ducklake тоже сдвинулось")

## Problem

The pin is 7304f7b (spec 131). The head of `v2.0-cyanoptera` is f8f3f4d (2026-10-16), 69 commits later, and tresor
moves to it. With it, duckdb moves quack from 974927a to e7a9be3, which is 110 commits of quack. Those carry the fix
spec 105 patched in, and they also change the server our quack door embeds.

## Design

- **duckdb 7304f7b → f8f3f4d.**
- **quack 974927a → e7a9be3**, the submodule's own pin, for the client loadable and for `third_party/quack` alike.
  - Spec 105's client patch leaves, because e7a9be3 carries duckdb-quack#305.
  - The embedded server's copies are regenerated by `sync.py`, which follows upstream's renames:
    - the server's `session_id` is now `connection_id`;
    - the FETCH request's fields are read through accessors (`AckIndex()`, `BatchIndex()`, `QueryUUID()`);
    - `quack_fetch_producer_buffer_bytes` is now `quack_server_stream_buffer_bytes`, and its getter lives in a new
      `quack_settings.cpp`, generated as `acl_embed_settings.cpp`.
  - **acl's setting keeps its name**, `acl_quack_fetch_producer_buffer_bytes`: an operator's configuration does not
    break at a pin bump.
  - quack serves HTTPS itself again, with a generated self-signed key and certificate pinning in the client
    (0572326). The door keeps its own TLS listener (spec 063). The client pins only when told a fingerprint, so a
    client of the door verifies its certificate as before.
- **The scanners at their mains** (spec 131's rule):
  - ducklake 4e923e2 → ca86db0, DuckLake v1.1: a catalog at 1.1-dev1 must be migrated;
  - duckdb-postgres ed73241 → c0f5a3c, which is also duckdb's own pin now;
  - mssql-extension 7c75db2 → 75e0fb6, its main re-pinned to f8f3f4d by its own session (no code change).

acl-otel, tresor and hugr-node follow the same day.

## As built

- **acl's own code**: three includes of `quack_settings.hpp`, where quack's setting defaults and getters now live
  (ef9231a), and the renamed default `QUACK_SERVER_STREAM_BUFFER_BYTES_DEFAULT`. Nothing else in acl changed.
- **`sync.py`**: the renamed literals, anchors and patch bodies (`connection_id`, the FETCH accessors), plus the new
  generated `acl_embed_settings.cpp`, listed in `acl_sources.cmake`. All eight acl hooks are in the regenerated server,
  as before.
- **The client patch is gone**: `patches/quack/` and its apply / revert step leave `extension_config.cmake`, which now
  reads like duckdb's own quack block (spec 105 addendum).
- **DuckLake v1.1** refuses a 1.1-dev1 catalog ("To automatically migrate, set AUTOMATIC_MIGRATION to TRUE"). CI
  starts empty. A developer's persistent catalog is recreated once, as the comment in `extension_config.cmake` says.
- **Found by CI**:
  - **The embed without TLS.** quack's headers now name `duckdb_httplib_openssl` themselves: the server's member and
    the pinned client's. The linux job builds acl without OpenSSL, where only `duckdb_httplib` exists. The
    namespace shim (`acl_quack_httplib_ns.hpp`) now aliases that way too. All ten embed TUs compile without TLS.
  - **The distribution build took a prebuilt duckdb.** extension-ci-tools a90d6d4 (2026-10-15) hands the build a
    prebuilt static duckdb (`DUCKDB_PREBUILT_LIBRARY`), which leaves no libduckdb for test-cpp. That build is the
    only place test-cpp runs on Windows and macOS. acl's Makefile overrides the two variables and builds duckdb
    from the pin as before; ci-tools stays unpinned.
- **The gate**, all green:
  - `test/sql/*`: 9563 assertions in 104 test cases;
  - test-cpp: 26;
  - test-flight: 8 scripts;
  - test-e2e: postgres, mssql, ducklake and the pair, plus types;
  - test-integration: 539 assertions;
  - harness, schema-check, the thread_local and fold lints, clang-format.
