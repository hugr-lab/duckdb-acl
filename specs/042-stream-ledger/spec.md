# Spec 042: the stream ledger — bulk loading through the door, under the policy

- **Status**: implemented
- **Date**: 2026-08-22
- **Author**: hugr-lab

## Summary

Spec 041 refused streamed ingest through the quack door, because the statement that writes it is
generated by the server, carries no principal, and cannot be enforced. This makes it work instead of
refusing it: the generated statement already carries quack's connection id inside its stream id, and
that id is already bound to a session — so the principal is recovered from the statement itself, and
what follows is an ordinary `INSERT … SELECT` through the rewriter we already have. The door-specific
part is a lookup; the rest is making a positional, name-less stream into a projection whose width is
checked rather than trusted.

## Problem

Bulk loading is a large part of what a client/server protocol is for, and today it is refused.

quack pushes a small `INSERT … VALUES` to the server as a statement, so it goes through the
authorization callback, gets our prefix, and is enforced. A bulk `INSERT … SELECT` does not: it goes
down `SEND_DATA`, where the server generates

```sql
INSERT INTO <schema>.<table> SELECT * FROM scan_data_from_quack_client('<connection_id>:<uuid>')
```

on the client's own connection, **unprefixed**. Spec 041 measured what that statement does when it is
allowed to run — it wrote 5000 rows carrying a tenant the principal's own grant forbids — and now
refuses it in the parser override. The refusal is correct and stays correct; it is also the whole
reason a client cannot bulk load.

## Design

### The lookup: the principal is already in the statement

`QuackStreamRegistry::MakeId` builds the stream id as `connection_id + ":" + uuid`, and
`acl_quack_authenticate` already binds quack's connection id to a session handle (spec 040). So the
generated statement carries, in a string literal, the key to the principal that caused it. Nothing has
to be journalled ahead of time — the "ledger" is a lookup, and the store already holds the map.

At the one place every unprefixed statement passes — where spec 041 throws — the override instead:

1. sees that the statement **calls** `scan_data_from_quack_client` (the existing cheap test);
2. parses it (under the existing `AclParseGuard`) and reads the scan's single constant argument;
3. splits the stream id at the **first** `:` and takes the connection id;
4. resolves it through `SessionHandleFor` → `SessionPrincipal`;
5. rewrites the statement under that principal, exactly as a prefixed one.

If any step fails — no session, expired, malformed id, more than one such call, anything unexpected —
it throws as it does today. **The refusal is the default and the rewrite is the exception**, not the
other way round.

### The shape: a positional stream, made honest

`scan_data_from_quack_client` binds its columns as `col0, col1, …` — the client's names do not travel,
and neither does the client's column list: `SendDataRequestMessage` carries connection id, schema,
table, chunks and query uuid, and nothing else. So the stream can only be read **positionally**, and
the rewrite must make that positional reading safe rather than assume it.

Two mechanisms, both of which fail loudly:

- **The insert names its columns.** The list is the principal's writable columns in publish order
  (spec 035), which is the shape the client saw when it built its insert. duckdb then checks the
  source's width against that list, so a stream that is wider or narrower than the published shape is
  an error, not a silent misalignment. This is why the list must be supplied and why supplying it
  blindly was refused in 041.
- **Injections replace a position, they do not re-project.** Where the grant assigns a value
  (`tenant = acl_claim('tenant')`), the source becomes
  `SELECT * REPLACE (<expr> AS col<i>) FROM scan_data_from_quack_client('<id>')`, with `i` the
  position the assigned column occupies in the list above.

  Why that shape and not the general one: measured, duckdb's positional column alias — which the
  ordinary injection path uses — **errors when the alias list is longer than the source** (a narrow
  stream is caught) but **silently ignores a source column too many** (a wide stream loses a column
  without a word). The first is what protects a client that mis-numbered; the second is the failure
  mode this layer refuses everywhere else, and a generated statement has nobody to be told about it.
  `*` keeps the width intact so the insert's own width check catches the wide case, and `REPLACE`
  refuses a column that is not there, so both directions are errors and neither is a shifted row.

  Applied only on the drain path, where the source is known to be quack's scan with `col<i>` names. An
  ordinary `INSERT … SELECT` keeps the general path: its source's column names are the client's own,
  so there is no position to name.

Everything after that is machinery that exists: caps gate the verb (`insert`), the grant's predicate is
AND-ed and checked where the row is written (spec 024), masks and computed columns are already
excluded from the writable set.

### The one exemption, and how narrow it is

`scan_data_from_quack_client` is on the denylist for a principal (spec 041), and it has to stay there —
otherwise a client reads somebody else's stream by id. But the drain statement is rewritten *under the
principal*, so the gate refuses the very statement we are trying to enforce.

The exemption is therefore bound to a single value: `Principal::ingest_stream`, set only by the drain
path and only to the id it recovered the principal from. The gate is not opened; a call whose argument
is exactly that id is passed through, and any other call — a second stream, another connection's id, a
non-constant argument — falls to the gate and is denied. A principal that arrives any other way (a
gateway prefix, a session prefix, a role prefix) carries an empty `ingest_stream`, so the exemption
cannot be reached from a statement anyone wrote.

### What a writable ingest actually requires

Measured while implementing, and worth stating because it constrains how an object must be modelled:

- **The object must be writable**, i.e. RENAME form. Declaring `COLUMNS` on the *object* makes it a
  projection, and a projection is read-only by construction (spec 001) — so a narrowed object refuses
  a bulk load exactly as it refuses any other write.
- **The column policy must come from the grant.** A grant with a predicate but no `COLUMNS` has no
  publish order, and spec 024 then refuses the write for a good reason: an unnamed column has no value
  for the predicate to judge. So a confined, writable object is modelled as a plain object plus a grant
  that states its columns — which is also the shape that makes the positional list meaningful.

### Still open

- **What a client's column subset does.** `INSERT INTO remote.main.orders (tenant) SELECT …` loses its
  column list on the wire — `SendDataRequestMessage` carries connection id, schema, table, chunks and
  query uuid, and nothing else. Whether duckdb's insert plan then produces full-width chunks or narrow
  ones decides whether that is an ordinary case or an error. The width checks above make it an error
  either way rather than a shifted row; what is missing is an error that says so in those words.
- **Ordered vs unordered streams.** quack signals `NO_ORDER` for an unordered stream so the planner
  picks a parallel insert. The rewrite wraps the source and does not re-order it, and the 5000-row
  round trip lands in full — but no test pins the parallel plan specifically.

## Enforcement & security

- **Fail-closed by default.** The path that ends in a rewrite is entered only when every step
  succeeds; every other outcome throws, including the ones that look like accidents (a stream id
  without a `:`, a session that has expired between the first row and the drain, two scan calls in one
  statement).
- **The connection id is quack's bearer credential, not ours.** Recovering a principal from it grants
  exactly what that connection already had: quack resolves every message through the same id. The
  ledger does not widen the credential, it reads it.
- **A client cannot author the statement.** `scan_data_from_quack_client` is on the denylist for a
  principal (spec 041), and the generated statement is the server's own text; the id in it is the
  server's too.
- **The golden rule holds**: the rewrite adds no query parameters — `* REPLACE` and the column list
  are text we compose from policy, and the claim values are baked as constants exactly as elsewhere.
- **The 041 fence stays.** Nothing here removes the refusal; it narrows it to "a stream whose
  principal cannot be recovered".

## Testing

`test/sql/acl_quack_door.test` (45 assertions) carries the parts that need no server, alongside the
door's own: a stream id naming no connection is refused; a connection nobody bound is refused; two
streams in one statement is refused; the name as ordinary text is **not** a call and must not be
mistaken for one (the resolver embeds a looked-up name as a literal in its own catalog SQL — this is
how the first, blunter fence was caught); and where the principal *is* recovered, the write is judged
as that principal's, so a role holding only `select` is refused for want of the capability — which is
also what proves the recovery happened. That case uses `conn-1:aaaa:bbbb`, so it pins the split at the
**first** colon too.

`test/sql/integration/acl_quack_ingest.test` (32 assertions, needs `ACL_QUACK=1`) — the live round trip:

- a bulk `INSERT … SELECT` of 5000 rows through an attached catalog **lands**, and the principal reads
  back its own slice;
- 5000 rows carrying a tenant the predicate forbids are refused where the value is written
  (`does not satisfy the grant`), and nothing of them is stored;
- under a grant that *assigns* the tenant, the same 5000 forbidden rows are accepted and stored with
  the claim's tenant instead — the client's value in that position is replaced, not trusted.

Its counterpart `acl_quack_ingest_denied.test` (25) keeps the dangerous layout from spec 041 — the
physical table in the server's default catalog under the published name — and now pins that what stops
the write is the write policy rather than the transport.

## Alternatives considered

- **A real ledger** — record `(stream id → principal)` in the authorization callback and look it up at
  drain time. This was the original plan, before the stream id turned out to carry the connection id.
  It is more state, with a lifetime nobody owns (when is an entry for a stream that never drained
  removed?), to hold a fact the statement already carries.
- **Ask quack to prefix the generated statement.** The right long-term fix and worth proposing
  upstream: quack already asks the authorization function about ingest, and could use the returned
  VARCHAR the way it does for `PREPARE_REQUEST`. Not ours to schedule, and the lookup makes us
  independent of it.
- **Refuse ingest permanently and tell clients to use `INSERT … VALUES`.** Honest, and gives up the
  reason to have a bulk protocol at all.

## Follow-ups

- **The probe now passes.** Spec 041 answered NULL to quack's ingest question, which stopped a stream
  before a row moved; with the drain enforced, that refusal would refuse everything. The cost is that a
  client whose write will be refused still streams its data first and learns at the end. Answering the
  question honestly — the principal's `insert` capability on that object — would refuse it early, and
  needs a capability check reachable without a statement to rewrite.
- **A statement the fence does not recognise is still unpoliced.** The fence keys on a call to
  `scan_data_from_quack_client`; if quack ever drains a stream by another name, an unprefixed write
  runs natively again. A stronger invariant would be to refuse *every* unprefixed write while a door is
  serving, which the operator's own console would feel — worth weighing when the door gets more use.
- **A session that expires mid-stream** ends the drain with an error and a partially written table,
  since the insert is one statement but the stream is many messages. Worth stating in the door's
  documentation: an ingest is atomic per statement, not per stream.
- **`CONNECT`/`DISCONNECT`** (duckdb PR #22732) will add another way for a client's statements to reach
  a server. If they travel as their own message type rather than through `PREPARE_REQUEST`, spec 041's
  rule applies again and the audit must be re-run. See `design/011-peg-parser-2.0`.
- **Concurrency and isolation across roles** is the next spec on this door: two clients under different
  roles reading and writing at once, a principal that must never reach another connection's statement,
  and what two concurrent drains into one table look like given that an ingest is atomic per statement
  rather than per stream. Everything here is single-client by construction of its tests.
